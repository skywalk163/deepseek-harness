## 2. 两个冲突与处置（本次新坑在这里）

### 2.1 `packages/sandbox/sandbox/src/index.ts` —— rc.1 同款「函数↔类共用 `}`」陷阱

两边都以一个 class 结尾，而 class 的收尾 `}` 落在冲突块**之外的共享尾部**；
git 把 `<<<<<<<` 放在 JSDoc 开头、`=======` 放在上一个 class 的 `this.name = ...` 之后，
于是「保留两边」会立刻少花括号（rc.1 那次炸出 58 条 TS 报错）。

| 侧 | 内容 |
|---|---|
| ours (fork) | `sandboxUnavailableHint()`（FreeBSD 感知文案 + `DSH_JAIL_RUN_BIN` 探测）、`SandboxUnsupportedPolicyError`（`SANDBOX_UNSUPPORTED_POLICY`） |
| theirs (rc.3) | `SANDBOX_PREPARATION_ERROR_CODES` / `SandboxPreparationErrorCode` / `SandboxPreparationError`（`SANDBOX_PREPARATION_FAILED`、`SANDBOX_INVALID_TEMP_ROOT`） |

处置：**两块都保留**，手工补齐 `SandboxUnsupportedPolicyError` 自己的 `}`、
再接 rc.3 的新常量/类型/类，共享尾部只留一个 `}`。
`SandboxUnavailableError` 的 `super(...)` 里对 `sandboxUnavailableHint()` 的调用（fork 加的）
在合并后的文件里**仍在**，没有被 rc.3 的内联通用文案覆盖。
校验：`node -e` 数 `{`/`}` → 40/40 平衡；`pnpm exec tsc --noEmit -p packages/util/ripgrep/tsconfig.json` → 0。
（`-p packages/sandbox/sandbox/tsconfig.json` 会报 3 条来自**未构建 `lib/types`** 的
TS6305/TS4112/TS2339，全在没动过的 `src/escalation.ts`，属陈旧产物，全量 build:lib 会消掉。）

### 2.2 `packages/fs/tool-fs-search/src/search-core.ts` —— ⚠️ 架构迁移，最重要的一条

**这不是普通的「两边都改」，是上游把功能搬走了**：

- rc.3 新增包 `packages/util/ripgrep/`（`@deepseek-ai/dsh-util-ripgrep`），
  `resolveRgPath` / `spawnRipgrep` / `readRipgrepLines` 全部搬进 `src/index.ts`；
  `search-core.ts` 只剩
  `import { spawnRipgrep } ...` + `export { resolveRgPath } from '@deepseek-ai/dsh-util-ripgrep'`。
- fork 的 FreeBSD 回退（`DSH_RIPGREP_PATH` → packaged path 存在性探测 → 系统 `rg` on PATH →
  **不 memoize**，让 `pkg install ripgrep` 后下一次搜索就生效）原本写在 `search-core.ts`。
- git 的重命名检测把 fork 的 `rg-sidecar.spec.ts` 认成新包的 `path.spec.ts`，
  所以**自动合并后的测试文件仍带着 FORK NOTE、仍断言** `existsSync(dependency.rgPath)` /
  `PATH` 隐藏 / `DSH_RIPGREP_PATH` 清理；但新包 `src/index.ts` 是**纯上游实现，没有回退**。
  若此时只跑编译，测试会红；若「保留 ours 的 search-core.ts」，则
  `search-core.ts` 会同时 `export { resolveRgPath } from ...` 和本地 `export function resolveRgPath`
  → 重复导出，且真正的 spawn 走的是新包，回退是死代码。

**处置（分两步）**：

1. `git checkout --theirs -- packages/fs/tool-fs-search/src/search-core.ts`
   —— 接受上游的「瘦」版本，删掉 fork 在旧位置的死实现。
2. **把 fork 的回退重新移植到新家** `packages/util/ripgrep/src/index.ts`：
   - 保留上游的 `spawnRipgrep` / `readRipgrepLines` 一行不动；
   - `resolveRgPath()` 改成 `return resolveRgPathUncached()`（不 memoize）；
   - 新增 `resolveRgPathUncached()` / `resolvePackagedRgPath()`，按 §2.2 开头那套顺序解析；
   - 顺序里 `existsSync(packaged)` 探测是关键：FreeBSD 上 `@vscode/ripgrep` 直接
     `THROWS: Could not find @vscode/ripgrep-freebsd-x64`，必须 catch 后落到系统 `rg`。
   - **顺手修了 fork 原实现的一个小瑕疵**：系统 rg 探测从
     `execSync('command -v rg || which rg')` 改成 `execSync('command -v rg')`
     —— 本机 FreeBSD 没有 `which`，旧写法每次解析都往 stderr 打
     `/bin/sh: which: not found`（不影响结果，但脏）。`command -v` 是 POSIX 内置，够了。

> 教训（写进 runbook）：**解冲突前先确认「这段逻辑在这轮上游里是不是被搬走了」**。
> 判据：`git diff --name-status <base>..<new-tag> -- <file>` 里有 `R`/新增包，
> 或 `grep -rn <符号> packages/` 发现出现了一个新 owner。
> 只看冲突标记里的「ours/theirs 文本」会得出「留我们的」这个看似合理、实则把功能弄丢的结论。

### 5.1 第一次跑的 `native-tests` 失败：不是回归，是本机缺 `npm`

4 个失败用例全在 `native/system/test/release-packing.test.js`（#53/#54/#55/#57），
错误统一是 `Error: spawnSync npm ENOENT`。根因链：

- rc.3 的 `native/system/scripts/pack-release.mjs:101` 对**平台包**用 `run('npm', ['pack', ...])`
  （entry 包才用 `pnpm`）；
- 本机 FreeBSD 上 `/usr/local/bin` 只有 `node` / `pnpm` / `corepack`，**没有 `npm` 可执行文件**
  （`/usr/local/lib/node_modules/npm/` 目录残缺，无 `package.json` / `npm-cli.js`）；
- 而 `pack-release.mjs` 与 `release-packing.test.js` 在 fork HEAD(rc.1) 与 rc.3 tag 里
  **逐字节相同** —— rc.1 那次 57/57 是在 1.5 上跑的（那台有 npm），与本次合并无关。

处置（**不改任何 fork 源码，只补本机环境**）：corepack 自带可用 npm（12.2.1），
但它检测到项目 `packageManager: pnpm@...` 就拒绝执行 `npm`。于是加一个
`~/.local/bin/npm` 包装（脚本的 PATH 含 `$HOME/.local/bin`）：

```sh
#!/bin/sh
# corepack 的 npm 需在真实路径调用（shim 相对 $0 找 ../dist/npm.js，symlink 会断），
# 且要绕开 pnpm 项目的 packageManager 检查；全程离线，不联网下载。
COREPACK_ENABLE_PROJECT_SPEC=0 COREPACK_ENABLE_DOWNLOAD_PROMPT=0 \
  exec /usr/local/lib/node_modules/corepack/dist/npm.js "$@"
```

验证：`npm --version` → 12.2.1；`npm pack --dry-run --json native/system/packages/freebsd-x64` → 0；
`pnpm --dir native/system test` → **# pass 57 / # fail 0**。

> runbook 待办：把「0.88 上跑 `sync-build-verify.sh` 前先确认 `command -v npm`」
> 写进脚本 preflight 或 `TASK-LOG` 模板，否则下次换机又会在同一处假红。

### 9.2 `freebsd/push.sh` 参数化

原版 6 处写死 1.5：`/home/workbuddy/.../.env`、`cd /home/workbuddy/...`、
github SSH key 路径、gitea 基址 `192.168.1.5:3000`、`push github/gitea` 远端名。
现在全部可推导/可覆盖：

| 原来写死 | 现在 |
|---|---|
| 仓库根 | 从 `$0` 推导（`dirname $SCRIPT_DIR`），并校验 `.git` |
| 凭据文件 | `$DSH_ENV` → `$REPO_ROOT/.env` → `$HOME/dswork/.env` → 1.5 路径 |
| `. .env` 整体 source | **逐键 `sed -n 's/^KEY=//p'` 读取**（本机 `.env` 有 `15SSH_HOST=` 这类非法标识符行，`set -a` 下会刷一串 command not found） |
| github SSH key | `$DSH_GITHUB_SSH_KEY` → `~/.ssh/id_ed25519_github` → `~/.ssh/id_ed25519`，都不可读则不传 `-i` |
| gitea 基址/凭据 | `$DSH_GITEA_URL` 或从 `.env` 的 `gitea=http://user:token@host:port/...` 解析；也可用同名 remote |
| `push github|gitea|origin`（要求远端名存在） | 有同名 remote 就用，否则回退到显式 URL；gitcode 从 `origin` 的 URL 推 |
| 无 | 新增 `--dry-run` / `--only <远端>` / `--no-tag` / `--verify-only`；末尾自动三远端 `ls-remote` 复核 sha；日志与回显统一 **redact 令牌** |

实测（本机 fb98/0.88）：

- `--verify-only` → 三远端 6 个 ref 全 `OK`，`RESULT: OK`
- `--dry-run` → 正确打印三条推送命令、令牌已 redact、无泄露
- `--only gitcode` / `--only gitea` / `--only github` → 真实推送均 `OK`（幂等 Up-to-date）
- `--no-tag` → 不推也不校验 tag
- `--bogus` / `--only`（缺参）→ 退出码 **2** + 明确报错

> 这一版在 1.5 上同样能用：它会先找 `$REPO_ROOT/.env`，找不到再退回
> `/home/workbuddy/github/deepseek-harness/.env`，github key 也会优先找
> `id_ed25519_github`。行为与原版一致，只是不再绑死那台机器。
