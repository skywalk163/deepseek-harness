## 3. 合并后的两个 fix（都是实测炸出来的）

### 3.1 `fix(freebsd): close sandboxUnavailableHint() body` —— `5c6ea2e21f`

解 `sandbox/src/index.ts` 时把「我们的函数」与「上游新增类」拼接，**两段共用了冲突块尾部那个
`}`**，于是函数体少一个右括号：

```
packages/sandbox/sandbox/src/index.ts(225,1): error TS1005: '}' expected.
```

后果不是一处报错，而是 **58 条**：`SandboxProvider` / `SandboxUnsupportedPolicyError` 等
导出全部「找不到」，`sandbox-local`、`sandbox-ssh`、`ptc-runtime-*` 一片 TS2305/TS2339。
**教训**：解「函数 ↔ 类」相邻冲突时，先数花括号再跑 tsc；`node -e` 数 `{`/`}` 平衡只要 1 秒。

### 3.2 `fix(freebsd): raise build heap to 8 GiB` —— `7b82a64cac`

`build:lib` 两次都以 **exit 134（SIGABRT）** 失败，日志尾部是真正的 V8 OOM：

```
FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory
[85086:…] Mark-Compact 4042.2 (4136.4) -> 4027.7 MB …
```

- **不是** OOM killer（那是 exit 137 + `/var/log/messages` 里的 `was killed`），是 **V8 堆上限**。
- 根因：fork 的 4 GiB 上限（当年为 8 GB 的 1.5 设的）撞上上游新版 client 打包（tsdown 单包动辄
  500–750 kB，webworker-runtime 甚至 751 kB）。0.88 有 64 GB，4 GiB 纯属自我设限。
- 修法：`build:lib:host` / `build:lib:client` 一并升到 `--max-old-space-size=8192`，
  并给 client 的 `tsdown` 加 `NODE_OPTIONS=--max-old-space-size=8192`（tsdown 是独立进程，
  不吃 tsc 那个 flag）。`freebsd/audit-merge.sh` 的断言同步放宽成
  `grep max-old-space-size=`（不再钉死 4096）。

## 6. `jail_attach: Operation not permitted` —— 已定位并修复

**这不是本次合并引入的**（`sandbox-local/src/index.ts` 相对 rc.3 只改了 4 行：一个 import +
windows-acl 的策略守卫，FreeBSD jail 的路径 / argv / 探针逻辑一字未动），是 fork 自带 helper 的
一个真实缺陷，只是以前一直没在「父进程长期存活」的场景里被触发。

### 根因

`jail(2)` 的 ERRORS 段写得很直白：

> Further `jail()`, `jail_set()`, `jail_attach()` … call `chroot(2)` internally, so they can fail
> for all the same reasons. **In particular, they return the `[EPERM]` error when the process to
> join a jail has open directories.**

而 harness 的 subprocess 层是用 **detached（setsid）** 方式拉起受限命令的
（`packages/subprocess/subprocess-local/src/spawn.ts`：`detached: platform !== 'win32'`），
它的 node 进程本身持有若干**打开的目录句柄**，这些 fd 会跨 exec 继承到 helper 里。于是：

```
CHILD_PRE jid=55 euid=0 cwd=/home/skywalk/github/deepseek-harness
  FD 19 dir=1 mode=40000     ← 一串目录 fd（S_IFDIR）
  FD 21 dir=1 mode=40000
  …
ATTACH_FAIL errno=1 (Operation not permitted)
```

对照实验把这条锁死了：**shell 里手工调用同一个二进制永远成功**（只有 0/1/2 三个 fd、没有目录句柄），
只有从 harness 里被 spawn 出来时才失败；`verify-sandbox.mjs` 也是手工 spawnSync，所以一直 10/10。

### 修法（`freebsd/dsh-jail-run.c`，其余逻辑不动）

在子进程 `jail_attach()` **之前**，把继承来的**目录** fd 全部关掉（文件 / 管道 / socket 保持原样，
避免影响 harness 的 control fd）：

```c
/* jail_attach() performs a chroot(2) internally, and chroot(2) fails with
 * EPERM when the calling process holds an OPEN DIRECTORY DESCRIPTOR. */
{
  int maxfd = getdtablesize();
  if (maxfd > 65536) maxfd = 65536;
  for (int fd = 0; fd < maxfd; fd++) {
    struct stat st;
    if (fstat(fd, &st) == 0 && S_ISDIR(st.st_mode)) close(fd);
  }
}
```

**验证**（0.88，修复版 helper）：

- `verify-sandbox.mjs` → **PASS=10 FAIL=0**（没有回退）；
- `dsh headless --permission-mode workspace-write "用 bash 执行 echo hi-rc1"` →
  工具**真的跑起来了**，模型答 `hi-rc1`，`SANDBOX_UNAVAILABLE` 消失。

> 附带结论：**helper 必须随源码重编安装**。0.88 上 `/usr/local/sbin/dsh-jail-run` 还是 2026-09-23
> 的旧二进制、`/var/dsh-jail-run` 是 2026-08-16 的，两者都早于这次修复；`freebsd/build-new.sh`
> 只编到 `~/dsh-jail-run.new`，`install` 那步要 root 手动做。
